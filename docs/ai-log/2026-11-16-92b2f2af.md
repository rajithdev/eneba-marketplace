## Data model

An offer is one seller's price for one product, and a key is one unit of stock belonging to an offer.

```
platforms        id, name, slug
regions          id, name, slug
products         id, slug, name, description, cover_image_url, platform_id, region_id,
                 type, release_date, sales_count          (trigram index on name)
sellers          id, name, slug, rating, sales_count
offers           id, product_id, seller_id, price_cents, original_price_cents, is_active
                 unique (product_id, seller_id)
license_keys     id, offer_id, code, status (available|sold), order_item_id, sold_at
users            id, name, email, password
orders           id, user_id, status (pending|paid|failed), total_cents,
                 payment_reference, idempotency_key, paid_at
order_items      id, order_id, offer_id, product_id, product_name, seller_name,
                 unit_price_cents, quantity
homepage_blocks  id, type, title, position, config (json), is_active
banners          id, title, subtitle, image_url, link_url, position, is_active
```

- **Stock is not a column.** It is the count of available keys, so it cannot drift from reality.
- **Cheapest price is computed at query time**, not stored on the product. At this data size that is fast and always correct; storing it is the path at scale.
- **Money** is integer cents in a single currency (EUR).
- **Order items snapshot** the product name, seller name, and price, so history survives later price changes.
- **Best sellers** sort by `sales_count`, which is seeded and then incremented by real purchases.
- **Deals** are offers where `original_price_cents` exceeds `price_cents`.

## The three areas you flagged

- **Offers:** the product page lists every seller's offer with price, rating, and stock. The cart holds offers, not products, because the buyer chose a seller.
- **Search:** results rank by prefix or substring match first, then trigram similarity, then popularity. Queries under three characters fall back to prefix matching, where trigrams are weak.
- **Checkout:** `POST /api/orders` runs in one database transaction:
  1. Re-price from current offers; if the total changed, return 409 with a fresh quote.
  2. Lock the needed keys with `FOR UPDATE SKIP LOCKED`; if there are too few, return 409.
  3. Charge the fake gateway; on decline, return 402 and sell nothing.
  4. Mark keys sold and the order paid.

  An `Idempotency-Key` header makes a double-click return the same order. Because payment is synchronous, no reservation timers are needed.

  - The CDN cache criteria say a response is not cached if it contains `set-cookie`, which presupposes such responses are passed through. https://vercel.com/docs/caching/cdn-cache#cacheable-response-criteria
  - `has`/`missing` rewrite conditions can match on `cookie`, so the request cookie is visible at the routing layer. https://vercel.com/docs/project-configuration/vercel-json
  - Vercel runs its own community forum (Discourse, a cookie-session app) behind a single external rewrite plus a secret header. The post does not discuss cookies explicitly. https://vercel.com/blog/how-we-run-vercels-cdn-in-front-of-discourse (March 10, 2026)
- **Nothing found saying Vercel alters cookie attributes.** No source describes Domain/Secure/SameSite being rewritten or stripped. UNCONFIRMED either way. Practical consequence: the upstream must not emit a `Domain` attribute naming the onrender.com host; your host-only cookie is the right shape.
- **Reported failures and their causes:**
  - Next.js issue #29488 claimed `Set-Cookie` was dropped through a rewrite; the author later reported it was working and closed it, with no root cause and no maintainer reply. https://github.com/vercel/next.js/issues/29488
  - Next.js discussion #36987: a user could not stop cookies being forwarded on an external rewrite, i.e. the request `Cookie` header goes upstream as-is (user report, not staff). https://github.com/vercel/next.js/discussions/36987
  - edge-runtime issue #536: several `Set-Cookie` headers merged into one comma-separated header. That concerns `fetch` inside edge functions, not vercel.json rewrites. https://github.com/vercel/edge-runtime/issues/536
  - The common "cookie lost" reports in search results turned out to be third-party cookie blocking, fixed by adding exactly this kind of rewrite (third-party repos, anecdotal only).

## 2. Request headers, Host, size limits

- **Documented as sent to the external origin:** `x-real-ip`, `x-forwarded-for` (visitor IP), `x-forwarded-host` (host the visitor requested), `x-forwarded-proto`. https://vercel.com/docs/routing/rewrites#identifying-the-visitor-at-your-origin
- Vercel overwrites `X-Forwarded-For` rather than forwarding a client-supplied value. https://vercel.com/docs/headers/request-headers
- **Origin, Referer, Sec-Fetch-Site, Accept, Content-Type, X-XSRF-TOKEN, custom headers:** no official list of what is forwarded unchanged. UNCONFIRMED. Indirect support: the docs offer a transform to *delete* or *set* request headers on a route, which implies headers are otherwise forwarded. https://vercel.com/docs/project-configuration/vercel-json (Transform examples)
- **Host header received upstream:** UNCONFIRMED in docs. One open, unanswered bug report (Next.js middleware rewrite between two Vercel apps) observed `host` equal to the destination host. https://github.com/vercel/next.js/issues/67469 . INFERENCE: destination host, which Render needs to route to the service.
- **Size limits (documented):**
  - Any single request header, name included, max 32 KB; all cookies travel in one `Cookie` header so they share that 32 KB. https://vercel.com/docs/errors/REQUEST_HEADER_TOO_LARGE
  - URL max 14 KB. https://vercel.com/docs/errors/URL_TOO_LONG
  - Body size for proxied requests: nothing documented. The 4.5 MB limit is stated for Vercel Functions only. https://vercel.com/docs/errors/FUNCTION_PAYLOAD_TOO_LARGE . UNCONFIRMED whether any cap applies to external rewrites.

## 3. vercel.json for this case

**Ordering and filesystem precedence**
- The filesystem is checked before `rewrites` are applied, so built files (`/assets/*.js`, `/favicon.ico`) are served directly and never hit the fallback. https://vercel.com/docs/project-configuration/vercel-json (rewrites)
- Source confirms the compile order: user `routes`, then redirects, then headers, then a filesystem handler, then `rewrites` in array order. https://github.com/vercel/vercel/blob/main/packages/routing-utils/src/index.ts
- Vercel's own SPA example is a single `/(.*)` to `/index.html` rewrite. https://vercel.com/docs/frameworks/frontend/vite#using-vite-to-make-spas
- Recommended form, API rule first and the fallback excluding `/api` so ordering cannot matter:

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "rewrites": [
    { "source": "/api/:path*", "destination": "https://<service>.onrender.com/api/:path*" },
    { "source": "/((?!api/).*)", "destination": "/index.html" }
  ],
  "headers": [
    {
      "source": "/api/:path*",
      "headers": [{ "key": "x-vercel-enable-rewrite-caching", "value": "0" }]
    }
  ]
}
```

- Side effect (INFERENCE): a request for a missing asset, such as a stale hashed chunk after a redeploy, returns `index.html` with 200 instead of 404.
- Not asked, but it will bite: Sanctum registers its CSRF route at `/sanctum/csrf-cookie` (prefix from `sanctum.prefix`), outside `/api`. With only `/api` proxied, set that prefix to `api/sanctum` or add a second rewrite, and keep login/logout under `/api`. https://github.com/laravel/sanctum/blob/4.x/src/SanctumServiceProvider.php

**Root Directory**
- The docs say vercel.json belongs in the project's root directory, and the monorepo docs show per-app files such as `apps/web/vercel.json`. So `web/vercel.json` is the one read when Root Directory is `web`. https://vercel.com/docs/project-configuration/vercel-json , https://vercel.com/docs/monorepos
- I did not find a sentence stating outright that a repo-root vercel.json is ignored when Root Directory is set; treat that as implied.
- Root Directory also sets the install path; by default the build can still reach files outside it. https://vercel.com/docs/builds/configure-a-build#root-directory

**Vite preset defaults**
- Detected when `vite` is a package dependency. Build command `vite build` (dashboard placeholder: `npm run build` or `vite build`), output directory `dist`, env prefix `VITE_`. https://github.com/vercel/vercel/blob/main/packages/frameworks/src/frameworks.ts
- The build-settings page says the build command can defer to the `build` script in package.json (shown for Next.js; not stated specifically for Vite). https://vercel.com/docs/builds/configure-a-build

## 4. CDN caching of proxied responses

- The opt-out is a **vercel.json `headers` rule on the source path**, not a header from the origin: key `x-vercel-enable-rewrite-caching`, value `0`, on `/api/:path*` (as in the config above). Value `1` is the opt-in for older projects. https://vercel.com/docs/routing/rewrites#disabling-caching-for-rewrites-to-external-origins
- Default-on applies to projects created on or after April 6, 2026. https://vercel.com/changelog/vercels-cdn-now-respects-cache-control-headers-from-external-origins-by-default
- Laravel's default is confirmed: Symfony's `ResponseHeaderBag` emits `no-cache, private` when no Cache-Control is set (and `private, must-revalidate` if `Last-Modified` or `Expires` is present). https://github.com/symfony/symfony/blob/7.4/src/Symfony/Component/HttpFoundation/ResponseHeaderBag.php
- That already blocks caching: Vercel will not cache a response with `private`, `no-cache` or `no-store`, nor one carrying `set-cookie`, nor a non-GET/HEAD request. Your API responses meet at least two of these. https://vercel.com/docs/caching/cdn-cache#cacheable-response-criteria
- So the opt-out header is belt and braces. Keep it, in case a route ever sets a public Cache-Control.

## 5. Render's side

- All inbound traffic goes through Cloudflare and then Render's load balancers; apps see a proxy IP on the socket and should read `x-forwarded-for`; `CF-Ray` is forwarded. https://render.com/articles/how-render-handles-ddos-attacks (April 1, 2026)
- `X-Forwarded-For` is **appended to, not overwritten**, so the leftmost entry is caller-controlled on a public service; `CF-Connecting-IP` is overwritten by Cloudflare on every request. https://render.com/articles/host-pocketbase-on-render
  - A Render community thread reportedly says the same about appending; I only saw it in a search summary because the forum redirect would not load. https://community.render.com/t/forward-real-ip-when-rewrite-urls/933
  - INFERENCE for this chain: Laravel sees `X-Forwarded-For` as visitor IP (set by Vercel), then Vercel's egress IP, and `CF-Connecting-IP` is Vercel's egress IP, not the visitor.
- `X-Forwarded-Proto`, `X-Forwarded-Host` and `Host` handling: not documented by Render. UNCONFIRMED. Render's load balancer terminates TLS and forwards to the service's port (default 10000). https://render.com/docs/web-services
- **Request timeout:** Render web services allow HTTP responses to take up to 100 minutes. https://render.com/docs/render-vs-vercel-comparison . The binding limit in this chain is therefore Vercel's 120 seconds. https://vercel.com/docs/limits#proxied-request-timeout
- Free tier: spins down after 15 minutes idle, about a minute to wake, and Render shows a loading page to connecting browsers; behaviour for a proxied XHR is undocumented. https://render.com/docs/free

## 6. Secret header to the origin on Hobby

- Yes in plain vercel.json, and no plan restriction is stated for `routes` transforms or `env` expansion. UNCONFIRMED only in the sense that the docs are silent on plans rather than naming Hobby. https://vercel.com/docs/routing/rewrites#restricting-your-origin-to-vercel-traffic , https://vercel.com/docs/project-configuration/vercel-json (Transform object definition)
- Documented pattern: a `routes` entry with an external `dest` and a `request.headers` / `set` transform whose `args` is `$ORIGIN_SECRET` with `env: ["ORIGIN_SECRET"]`. `set` replaces any visitor-supplied value.
- `routes` may now be used alongside `rewrites` and `headers` (docs), and user routes run before the filesystem check and rewrites (source). Combined config for this case, assembled from those documented pieces:

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "routes": [
    {
      "src": "/api/(.*)",
      "dest": "https://<service>.onrender.com/api/$1",
      "transforms": [
        {
          "type": "request.headers",
          "op": "set",
          "target": { "key": "x-origin-secret" },
          "args": "$ORIGIN_SECRET",
          "env": ["ORIGIN_SECRET"]
        }
      ]
    }
  ],
  "rewrites": [
    { "source": "/((?!api/).*)", "destination": "/index.html" }
  ],
  "headers": [
    {
      "source": "/api/:path*",
      "headers": [{ "key": "x-vercel-enable-rewrite-caching", "value": "0" }]
    }
  ]
}
```

- Gotchas from the docs:
  - If the env var is not set in the project, the literal string `$ORIGIN_SECRET` is sent. Set it for every environment you deploy (Production and Preview).
  - Changing the variable needs a redeploy; rotate by accepting old and new values at the origin.
  - With `routes` plus `rewrites`/`headers` in one file, `src` matching is case-sensitive.
- Origin side: reject requests whose header does not match, using a timing-safe comparison, and exempt Render's health-check path (INFERENCE: health checks do not come through Vercel).
