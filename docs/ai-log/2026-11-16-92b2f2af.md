## Data model

An offer is one seller's price for one product, and a key is one unit of stock belonging to an offer.

```
platforms        id, name, slug
regions          id, name, slug
products         id, slug, name, description, cover_image_url, platform_id, region_id,
                 type, release_date, sales_count          (trigram index on name)
sellers          id, name, slug, rating, sales_count
offers           id, product_id, seller_id, price_cents, original_price_cents, is_active
                 unique (product_id, seller_id)
license_keys     id, offer_id, code, status (available|sold), order_item_id, sold_at
users            id, name, email, password
orders           id, user_id, status (pending|paid|failed), total_cents,
                 payment_reference, idempotency_key, paid_at
order_items      id, order_id, offer_id, product_id, product_name, seller_name,
                 unit_price_cents, quantity
homepage_blocks  id, type, title, position, config (json), is_active
banners          id, title, subtitle, image_url, link_url, position, is_active
```

- **Stock is not a column.** It is the count of available keys, so it cannot drift from reality.
- **Cheapest price is computed at query time**, not stored on the product. At this data size that is fast and always correct; storing it is the path at scale.
- **Money** is integer cents in a single currency (EUR).
- **Order items snapshot** the product name, seller name, and price, so history survives later price changes.
- **Best sellers** sort by `sales_count`, which is seeded and then incremented by real purchases.
- **Deals** are offers where `original_price_cents` exceeds `price_cents`.

## The three areas you flagged

- **Offers:** the product page lists every seller's offer with price, rating, and stock. The cart holds offers, not products, because the buyer chose a seller.
- **Search:** results rank by prefix or substring match first, then trigram similarity, then popularity. Queries under three characters fall back to prefix matching, where trigrams are weak.
- **Checkout:** `POST /api/orders` runs in one database transaction:
  1. Re-price from current offers; if the total changed, return 409 with a fresh quote.
  2. Lock the needed keys with `FOR UPDATE SKIP LOCKED`; if there are too few, return 409.
  3. Charge the fake gateway; on decline, return 402 and sell nothing.
  4. Mark keys sold and the order paid.

  An `Idempotency-Key` header makes a double-click return the same order. Because payment is synchronous, no reservation timers are needed.

## Ranking approach

One query (`Product::scopeSearch`) serves both the header suggestions (`GET /api/search/suggestions?q=`) and the store (`GET /api/products?q=`). The suggestions are therefore always the first six results the store would show, and a test asserts that.

**What matches.** The text is cleaned once (trimmed, lowercased, at most 80 characters and 6 words). Every word must match the product name, in any order:

| Word length | Matches when |
|---|---|
| 1 or 2 letters | it starts a word in the name |
| 3 or more | it appears anywhere in the name, or is a near miss of a word in it |

A near miss is `pg_trgm` word similarity of at least 0.5. I measured this on the catalog: the default 0.6 misses ordinary slips ("mincraft" scores 0.58), and 0.4 starts matching unrelated titles.

**Order of results:**

1. Tier: exact name or game title, then name starts with the term, then every word present, then typo matches.
2. Similarity score within the tier.
3. Purchasable before sold out.
4. Popularity (sales count).

Choosing another sort order (price, popularity, newest) re-sorts the same matches.

**Cost controls:**
- Suggestions take 5 queries and the store takes 6, whatever the input.
- Fewer than 2 characters is answered without touching the database.
- Suggestions are rate limited to 120 a minute per visitor.
- The trigram index is used for typo searches: 1 to 15 ms at 12,000 products.
- Rate-limit counters moved from the database cache to a file store, because counting each suggestion was costing 12 extra queries.

## Review of the existing models

The foundations held (stock is the count of available keys, one payment per order, one order per idempotency key, key states enforced by a constraint). Four things needed correcting, done as a new migration:

- **No order deadline.** Only the keys carried `reserved_until`; orders gained `expires_at`.
- **Unsafe expiry.** The original plan let the next buyer take overdue keys directly. If the first buyer had been charged and only our bookkeeping crashed, their keys would have been sold twice.
- **States not explicit enough.** Orders and payments gained `cancelled`; an unpaid order's payment is no longer labelled "failed".
- **Idempotency ignored the payload.** Orders gained `cart_hash`, so a reused key with a different cart is refused.

## Transaction design

A purchase is three steps in two requests:

| Step | Request | Transaction |
|---|---|---|
| 1. Reserve | `POST /api/orders` | One: re-price the cart, create the pending order and payment, hold the keys for 10 minutes |
| 2. Charge | `POST /api/orders/{id}/pay` | None open while the gateway is asked |
| 3. Record | same request | One: lock the order row, then keys, payment and order change together |

- **Order states:** `pending` → `paid`, `failed`, `expired` or `cancelled`. None is ever left once reached.
- **Payment states:** `pending` → `succeeded`, `failed` or `cancelled`.
- **Key states:** `available` → `reserved` → `sold`, or back to `available`.
- **Separation:** `InventoryAllocator` knows keys and nothing about payments; `PaymentGateway` knows charging and nothing about orders; `SettleOrder` is the only code that moves an order out of `pending`.
- **The safety rule:** the gateway decides a reference (the order's public id) once. The first charge or cancel fixes the outcome and every later call returns it. Keys are sold only after a confirmed charge and released only after a confirmed decline or cancellation.
- **No card form:** the buyer picks one of three test cards (approved, declined, insufficient funds), so no card data is ever asked for.

## Failure handling

| Situation | Outcome |
|---|---|
| Two buyers want the last key | `FOR UPDATE SKIP LOCKED`: one gets it, the other is told at once (409 with a fresh quote) |
| Same order request repeated or sent several times at once | One order; every copy gets it |
| "Pay" pressed repeatedly | One charge, keys delivered once |
| Price or stock changed | Nothing reserved; the cart shows what changed and the buyer must accept it |
| Payment declined | Keys back on sale immediately; retrying is a new order |
| Buyer never pays | The order expires: cancelled at the gateway first, then keys released |
| Crash after reserving | The buyer can still pay until the deadline, otherwise it expires |
| Crash after charging, before recording | The next request that touches the order records it; the buyer gets the keys even if they never return |
| Crash while recording | The transaction rolls back; same as the row above |
| Pay and cancel at the same moment | Exactly one wins, and every request reports that result |

Access: every order route needs a signed-in user, and someone else's order answers "not found". Keys appear only in a paid order's own response.

## 3. vercel.json for this case

**Ordering and filesystem precedence**
- The filesystem is checked before `rewrites` are applied, so built files (`/assets/*.js`, `/favicon.ico`) are served directly and never hit the fallback. https://vercel.com/docs/project-configuration/vercel-json (rewrites)
- Source confirms the compile order: user `routes`, then redirects, then headers, then a filesystem handler, then `rewrites` in array order. https://github.com/vercel/vercel/blob/main/packages/routing-utils/src/index.ts
- Vercel's own SPA example is a single `/(.*)` to `/index.html` rewrite. https://vercel.com/docs/frameworks/frontend/vite#using-vite-to-make-spas
- Recommended form, API rule first and the fallback excluding `/api` so ordering cannot matter:

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "rewrites": [
    { "source": "/api/:path*", "destination": "https://<service>.onrender.com/api/:path*" },
    { "source": "/((?!api/).*)", "destination": "/index.html" }
  ],
  "headers": [
    {
      "source": "/api/:path*",
      "headers": [{ "key": "x-vercel-enable-rewrite-caching", "value": "0" }]
    }
  ]
}
```

- Side effect (INFERENCE): a request for a missing asset, such as a stale hashed chunk after a redeploy, returns `index.html` with 200 instead of 404.
- Not asked, but it will bite: Sanctum registers its CSRF route at `/sanctum/csrf-cookie` (prefix from `sanctum.prefix`), outside `/api`. With only `/api` proxied, set that prefix to `api/sanctum` or add a second rewrite, and keep login/logout under `/api`. https://github.com/laravel/sanctum/blob/4.x/src/SanctumServiceProvider.php

```json
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "routes": [
    {
      "src": "/api/(.*)",
      "dest": "https://<service>.onrender.com/api/$1",
      "transforms": [
        {
          "type": "request.headers",
          "op": "set",
          "target": { "key": "x-origin-secret" },
          "args": "$ORIGIN_SECRET",
          "env": ["ORIGIN_SECRET"]
        }
      ]
    }
  ],
  "rewrites": [
    { "source": "/((?!api/).*)", "destination": "/index.html" }
  ],
  "headers": [
    {
      "source": "/api/:path*",
      "headers": [{ "key": "x-vercel-enable-rewrite-caching", "value": "0" }]
    }
  ]
}
```

- Gotchas from the docs:
  - If the env var is not set in the project, the literal string `$ORIGIN_SECRET` is sent. Set it for every environment you deploy (Production and Preview).
  - Changing the variable needs a redeploy; rotate by accepting old and new values at the origin.
  - With `routes` plus `rewrites`/`headers` in one file, `src` matching is case-sensitive.
- Origin side: reject requests whose header does not match, using a timing-safe comparison, and exempt Render's health-check path (INFERENCE: health checks do not come through Vercel).

1. Both `Set-Cookie` headers (session and `XSRF-TOKEN`) arrive at the browser as two separate headers with `Secure`, `HttpOnly`, `SameSite=Lax` and no `Domain` intact. Check in Safari and Chrome Incognito.
2. The browser's `Cookie` header reaches Laravel on the next proxied request.
3. `Origin`, `Referer`, `Sec-Fetch-Site`, `Accept`, `Content-Type` and `X-XSRF-TOKEN` reach Laravel unchanged. Sanctum's stateful check depends on Referer/Origin, and Laravel 13's CSRF check on `Sec-Fetch-Site`.
4. Which `Host` Laravel sees, and whether Vercel's `x-forwarded-host` survives Cloudflare and Render's load balancer (dump headers from a temporary debug route).
5. What `X-Forwarded-For` and `X-Forwarded-Proto` look like after the full chain, and what `$request->ip()` and `$request->isSecure()` return with `trustProxies(at: '*')`.
6. What the SPA receives when the Render service is asleep: a held request that succeeds within 120s, Render's HTML loading page, or a 502 `ROUTER_EXTERNAL_TARGET_ERROR`.
7. That the `routes` + `rewrites` + `headers` combination deploys cleanly and behaves as intended, including the secret header arriving with the expanded value.
8. That `x-vercel-cache` shows no HIT on any `/api` response.
9. That `web/vercel.json` is picked up with Root Directory `web` (visible immediately: `/api/...` proxies and deep links load).
10. Whether any body-size cap applies to proxied uploads, if the API accepts files.
